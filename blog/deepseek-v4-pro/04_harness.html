当大肥鱼凝视 SRE 的时候，它看到了什么

本章结论：dsh 极简模式与 V4 Pro 自身的策略存在摩擦

这部分主体在 PDF 长文里，此处仅简略说明；证据、详细分析，让读了 PDF 的 AI 来讲解吧

V4 Pro 没有好好学会 SRE 的用法

Invalid Arguments

SRE 中有的参数是可选的。

比如：view 的时候，new_str，old_str 等实际上不用给出。

但是 V4 Pro 会主动把它们写成 null：

str_replace_editor({
  "command": "str_replace",
  "path": "/app/input.tex",
  "old_str": "in a reserved way",
  "new_str": "in a quiet way",
  "file_text": null,
  "insert_line": null,
  "view_range": null
})

会产生：

=> INVALID_ARGS: Error: invalid arguments:
   "file_text" must be a string;
   "insert_line" must be an integer;
   "view_range" must be an array

dsh 解析 可选输入 时，只有一种期望的输入：

不填写这个输入

例如，上面的错误调用，能被 dsh 解析且不报错的写法是：

str_replace_editor({
  "command": "str_replace",
  "path": "/app/input.tex",
  "old_str": "in a reserved way",
  "new_str": "in a quiet way",
})

主实验里，有 6 条轨迹调用过 SRE，模型在其中的 5 条里都额外提交了 null。

Invalid Arguments 一共发生 6 次；有一个轨迹里，模型已经知道不能写 null 了，又犯了错。

从 JSON Schema 语义看，DeepSeek Harness 拒绝 null 并不违规：optional 与 nullable 是两回事。

问题在产品组合层面，V4 Pro 偶尔进入官方提供的 SRE 路径时，会反复生成这套官方 Harness 不接受的参数形状。

官方模型反复生成显式的 null，官方 Harness 又严格拒绝；两者单独都可以声称符合自己的协议，但组合起来持续制造了无效调用。1

何意味，傻鱼……

FS_NOT_OBSERVED

SRE 要求模型先用 sre("command" = "view", ...) 登记目标文件的观察状态，再用 sre("command" = "str_replace", ...) 进行修改。

dsh 不认可 bash 先读、再用 SRE 修改的操作

dsh 的 SRE 实际上有两层保护：

  1. old_str 必须要在文件里 唯一匹配 \rightarrow 模型必须给出正确的原文，才能修改
  2. 不跨 SRE / bash 的读写检测：必须先用 SRE 读过，才能用 SRE 写。

这不是唯一可行的设计。它提供版本新鲜度保护，但在持久 bash 与 SRE 并列的双工具配置里，也会把模型已经读过的文件判定为“未读”，制造一次额外的跨工具摩擦。

较为合理的如 Claude Code 的 SRE 类似物（v2.1.208 起）：允许模型通过 bash grep / cat 等其他工具先简单的读原文（限单文件、无管道的查看命令），再用 SRE 修改。

GLM-5.3 也在这里崴了脚，出现了好几次用 bash 读 + SRE 编辑后被报错退回的情况。不过综合来看，V4 Pro 的犯错率依旧出类拔萃：

【Linux 样本中，已经发生的 SRE 请求内的拒绝比例】

模型与数据 SRE 请求 显式 null 拒绝 FS_NOT_OBSERVED
V4 Pro 32 9（28.13%） 4（12.50%）
GLM-5.3 594 0（0.00%） 6（1.01%）

虽然 V4 Pro 的 SRE 调用次数少的惊人，但是 SRE 调用失败的次数也高的惊人啊……





















彩蛋：

关于 dsh 参考过的 Pi Agent，Pi 中没有“先读后写”检测，Pi 的 edit 工具靠的就是 old_str 的匹配。匹配的上，那就完成修改。

这也合理，模型既然能填对 old_str，那可以相信模型知道自己在改什么。

DSH 把 Pi 式唯一文本匹配与独立的观察版本约束叠加到一起，得到了一条比两者都更严格的修改路径；

这种额外保护有工程收益，也增加了 bash 与 SRE 并列时的跨工具成本。

在时间夹缝之中，SRE 起初没有计划与 bash 绑在一起

……那也怪不得 V4 Pro 不喜欢用 SRE 了……

彩蛋2：

主实验所用的 dsh 不允许可选参数写成 null，那么它的其他校验一定很严格吧……

no！

如果模型请求：

str_replace_editor({
  "command": "str_replace",
  "path": "/app/input.tex",
  "old_str": "in a reserved way",
  "new_str": "in a quiet way",
  "i_want_to_eat_big_white_rice": "dying to"
})

多出来的这个 i_want_to_eat_big_white_rice，dsh 会如何处理呢？

执行期丢弃！

模型不会收到报错，“幻觉出来的新参数名”反而畅通无阻；

大白饭会顺利 通过校验 、到达执行层，然后被工具体静默忽略。

于是模型就能吃得很香了。

当然，Claude Code 也是这么干的，所以无所谓

彩蛋3：

【实现对照】

这里不能简单说 DeepSeek Harness 违反了 JSON Schema：optional 不等于 nullable。
在主实验所用的 SRE schema 中，这些字段可以省略，但一旦显式出现，就必须具有对应的非空类型，因此 DSH 拒绝 null 是其参数规范的正常结果。
问题在于，这并不是同谱系编辑器唯一采用的兼容策略。
Anthropic 的 str_replace_based_edit_tool 参考实现将多项跨命令参数接收为可空值； 执行 str_replace 时，与当前命令无关的空字段不会在统一入口处触发拒绝，new_str=None 还会被解释为空字符串。
换言之，V4 Pro 生成的这种参数形状在 DSH 中不合法，却可以被另一种编辑器运行时接受。
严格校验本身可以合理，但“官方模型 + 官方 RL 适配 Harness”的组合仍未消化这处协议差异，最终把它变成了一次无效工具调用。

—— 这不是在替大肥鱼开脱。恰恰相反：

如果极简模式只是一个普通第三方 Harness，这可以解释为跨 Harness 迁移失败；

但当它被公开称为与 V4 Pro 的 RL 训练条件适配时，同一失配就需要额外解释。
