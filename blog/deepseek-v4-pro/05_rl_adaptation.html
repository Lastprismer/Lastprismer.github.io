有趣吗？我只看到了一只惨鱼……

本章推论：如果 V4 Pro 真的在极简模式下“适配”过，那一切都说得通了……

实际上说到这里，已经产生了一个重大偏差：

假设：V4 Pro “在 Linux 极简模式上训练对齐的比较好”

训练运行时是否与当前公开 Linux 实现逐项相同，仍然未知。

当前观测到的现象：

  1. V4 Pro 极度依赖 bash，不用 SRE；
  2. 很少的 SRE 请求里，V4 Pro 似乎不能很好的理解 SRE 的使用方法。

隔壁的 GLM-5.3 则是另一番景象：

  1. GLM-5.3 知道如何使用 SRE，没有对 bash 的夸张偏好；
  2. GLM-5.3 似乎比 V4 Pro 更了解如何使用 SRE：额外触发的 FS_NOT_OBSERVED，似乎更像 Harness 本身的过度设计所导致。

换言之，V4 Pro 似乎适配的不是很稳定；或者可以说，V4 Pro 在这个环境下，一直困于 疯狂使用 bash 的舒适区。

那就很奇怪了。V4 Pro 在这个场景下充分训练过，但是变成了独眼大肥鱼；

再加上 dsh 官方宣传 “极简模式是双工具编码 Agent……”

你别说，还真有可能。

听我慢慢分析：

假设的核心：

  1. 训练早期，策略以非零概率选择 SRE，并且尚未稳定掌握其参数与状态协议。
  2. 在训练使用的运行环境中，SRE 因无效调用、额外查看、更多轮次或任务失败而具有更低的有效回报。
  3. 后续训练数据或 rollout 的产生频率受当前策略影响；某条路径越少被选择，继续修正其调用协议的样本越少。

以下是详细解释：

如果前两个大前提成立，即使训练开始前，模型对 bash 还没有产生极端偏好，进入 on-policy Agent 后训练持续进行时，还是会变成独眼龙……

已知：

  • bash 很强！编译、测试、搜索，都得依赖 bash；

  • bash 可以替代 SRE 的生态位；

  • 摩擦 1：V4 Pro 在低频 SRE 请求中多次填写显式 null，但是主实验所用的 dsh 极简模式会拒收；bash 不存在“可选参数”；

  • 摩擦 2：少数轨迹中出现“Bash 已读 → SRE 修改”的跨工具路径，但是 dsh 会拒绝；bash 修改文件时不会被 Harness 无端截停

  • 两个摩擦都会触发，触发后一个报错 Invalid Arguments，另一个 FS_NOT_OBSERVED，均为 工具调用失败

那么，以最简单的工具调用惩罚作为例子：

如果这两类局部摩擦在训练中持续增加某条工具路径的错误概率、交互轮数、token 消耗或任务失败风险，
它们就可能降低选择 SRE 后的有效期望回报；
这个机制不要求训练系统显式设置一项“工具调用错误罚分”，也不依赖 PPO、GRPO 或其他具体算法。

如果训练目标之一是让模型稳定掌握这份双工具合约，理想的更新 应当修正 SRE 的调用参数和调用顺序 ；

但更容易出现的另一条更新路径，是 直接降低 SRE 的选择概率。

哎呦，还是大肥鱼说的容易理解。大肥鱼是对的。

都是瞎猜的，如果有训练日志，可以直接斩断我的假说。
