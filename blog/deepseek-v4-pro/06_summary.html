谁能用什么证据推翻这篇文章

到这里，最容易犯的错误，是把一条解释得通的因果链，当成已经发生过的训练历史。

社区已经吃了一堑，把 We 打成了“跑分信号”，现在还在无限冲刺。

这里我必须强调一下。关于后训练猜想部分：

  • 工具路由、模型自己填 null，以及状态摩擦是 真实观测结果；
  • 训练运行和环境、奖励与惩罚和策略自增强，纯属假说。

这套“后训练路径”是一个能够同时解释“低路由率”和“首次调用不稳定”的假说，即使贴出了 commit 记录和 DeepSeek Harness 文档，也不是 DeepSeek 训练过程的复原报告。

我也十分好奇，当前工具路由究竟怎样形成，是否来自后训练，实际情况可能远比我想象的复杂。

总结

我们直接观察到：

  • 在选取的 20 道 Terminal-Bench 2.1 任务上，标准与极简模式没有形成稳定的成绩领先；
  • V4 Pro 的语言形态强烈受首请求配置影响，完整口癖可以稳定区分两种配置；
  • Linux 极简模式下，V4 Pro 的工具请求近乎全部进入 bash，至少 GLM-5.3 不呈现相同路由；
  • V4 Pro 偶尔进入 SRE 时，确实遇到了“显式 null” 和跨工具观察状态两类摩擦。

我没承认这些：

  • We，电报体，工具调用均衡，能够提高或降低模型的任务能力
  • 任一社区插件无效
  • DeepSeek V4 Pro 的训练 rollout 的环境和公开的 dsh Linux 极简模式相同，所以我的猜想都是对的
  • 后训练导致的工具分化是真实发生过的

插件作者请狠狠反驳我

别光看灰测语气，盯着 Let’s、We、甚至未来的 I’m doing 了。

工具出现在 schema 中，不等于模型会使用；
首块出现 We need，也不等于某个高能力策略已经被保留。
插件若同时声称“恢复了完整工具能力”和“锚定了 RL 模式”，就至少应当测量这两个命题对应的工具行为与任务结果。

我万分期待插件社区能做出 好的工作流编排 作品，最终目标是提出能跨 Harness 复现的成熟工作流。

但这肯定是建立在广泛的实验、测试甚至问卷调查上的。

也别看完我这个报告后，捣鼓“如何让 V4 Pro 下能均衡地使用 SRE 和 bash”，这不一定有用

  • 对于工具调用坍缩，我能说的是：它与“双工具 Agent”的公开表述形成了明显矛盾；我的跑分没法证明“这会降低模型能力”
  • 真要证明，得覆盖多种任务，多次实验，用频数硬抗 Agent Trajectory 的高方差；但我不建议往这个方向深入：发一个新 Checkpoint，结论就不适用了，个人无需帮模厂承担这些“小支线任务”的成本
  • 如果真的有大佬针对工具分布进行了深入的测试，请给我一个 cite + 拉我观摩观摩，我很好奇真实结论

……

对 DeepSeek 倒是不敢提什么问题，简单问问：

  • 如果 bash 优先本就是 Harness + Model 正常的预期策略，那 str_replace_editor 在 DeepSeek Harness minimal 下的产品定位，具体是什么？

  • 我最低预期：既然极简模式被公开描述为 bash + SRE 的双工具 Agent，官方模型至少应当稳定掌握 SRE 的基本参数与状态协议。

普通用户……？

  • 最合理的做法仍然是用自己的真实任务比较交付结果，而不是追逐模型第一句话。

  • 不必为了让工具调用看起来均衡而修改 Agent；均衡不是目标，可靠完成任务才是。

  • 但无论是厂商还是插件作者，只要提出了关于 RL 模式、工具能力或机制 的主张，就应当保存并检查完整轨迹。

口癖是 prompt 和训练集的回声，工具目录是产品的宣传页；

只有完整轨迹，才是 Agent 真正留下的账本。
