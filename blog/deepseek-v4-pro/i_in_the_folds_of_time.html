注记❓ GLM 对 08-09 死循环的完整拆解（点击展开）
  • 🔵 死循环的转法（笔记 Problem 段的场景）：
    1. 模型先读过文件，观察账本记下版本 V（present）；
    2. 文件随后被外部命令删除；
    3. 模型再写这个文件：账本仍是 present(V)，写入走 replaceIfVersion，正确地被拒；按 08-03 的规矩，报错尾部追加 “re-read the file, then retry”；
    4. 模型照做，重新读：得到 FS_NOT_FOUND。旧实现里只有成功的读取和写入才发 fs/observed，读失败不记任何事件，账本原地不动；
    5. 再写：仍被当作 replaceIfVersion，仍被拒，报错仍是同一句。回到第 4 步。
  • 🔵 每一步都合规，状态却永远不变：补救文案指的路，被记账法本身堵死。这就是笔记所称的 unrecoverable loop：问题不在模型，在账本让「重读」变成无效动作。
  • 🟡 会话内最典型的「外部命令」恰恰是模型自己通过 bash 跑的 rm：bash 在沙箱 runner 中执行，对 fs provider 而言就是外部进程，删除不经过账本（机制推断：笔记原话只说 “an external command deletes it”）。
  • 🔵 修法：观察从「只有成功读取」扩成三态，unseen（没见过）/ absent（确认不存在）/ present（存在且有版本）。read 与 SRE 的 view/str_replace/insert 遇到文件不存在时，先同步发一条 absent 观察事件、再返回 FS_NOT_FOUND。此后账本为 absent，写入合法映射为 createIfAbsent（目标不存在时才创建），循环闭合。笔记标题即立场：“Filesystem absence is an observation”。
  • 🔵 附带的竞态：确认不存在之后再创建，仍可能在发布瞬间被其他进程抢先创建文件；因此 createIfAbsent 的检查被挪到发布点本身执行（本地实现用暂存目录加硬链接，E2B 用远端 ln -T）。
  • 🔵 Alternatives 段拒绝了「把死胡同保持 fail-closed」，理由原话：“the model-facing recovery instruction is then false”。
